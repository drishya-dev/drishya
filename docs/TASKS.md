# Product checklist

**The single current work list. Restructured 19 October 2026.** Builders and agents update this file in the same increment as the work: tick an item only when its stated scope is implemented and checked on actual sessions; add new feedback here before starting it. STATUS is the session log, CONTINUITY is the handoff, numbered reviews are evidence. They are not competing task lists.

**Claiming.** Before starting an item, claim its ID in the [STATUS](STATUS.md#claimed) table and push that to `main`; `node scripts/claims.ts` shows what is open and what is taken.

**How to read it.** §1 is the **priority order**: one line per item with its ID and tags. §3 holds the **detail** for every ID, grouped by category: problem, what to do, acceptance, where in the code. §4 archives every item completed before this restructure, verbatim.

`[x]` = implemented and locally checked within the stated limits. `[ ]` = unfinished. A checked item does not certify native accounts, every device, visual preference or release readiness.

Evidence for this restructure: [122 developer review](review/122-developer-product-review.md) (with builder corrections), [123 harness data audit](review/123-harness-data-audit.md), [124 Sacred Timeline spec](review/124-sacred-timeline-git-graph.md).

## 0. Rules for every item

1. **Product north star.** Drishya is the best *visualization of agent work* plus the *developer tools needed to understand it while it happens*. A developer should understand the change as it is made, not only after. Every item must serve that.
2. **Minimal by default.** The builder's design rule: the UI stays minimalistic and calm.
   - Do **not** add resident buttons or panels for a new feature. Put it in an existing owner (contextual hover, the ⋯ menu, Ctrl+K, a reader toolbar) unless it *replaces* something.
   - Any surface whose controls take more space than its content is a bug (see UI-5).
3. **Verify before changing.** Use the running app on actual Codex and Claude sessions and read the code before "fixing" anything. Several things that look wrong are deliberate (builder corrections, 19 Oct):
   - Toolbox→card connectors appear **on hover only**.
   - The passage layout **wraps** actions onto the next row with arrows from box to box. This is intentional; one infinite horizontal lane is rejected.
   - **File peek** (beside the agent) and **Workspace** (full view when not watching the agent) are two intended modes.
   - The **3D repository map** stays as an aesthetic surface for now.
4. **Truth.** Captured ≠ derived. A model's output is always labelled as generated and cites captured evidence. Missing data stays visibly missing. No invented links or locations ([AGENTS](../AGENTS.md) constraints).
5. **Every interaction has purposeful motion.** Every click, toggle, open and close gets a suitable, interruptible transition tied to its true origin, with reduced-motion and low-resource fallbacks (MOTION-1). Use the installed `emil-design-eng`, `animate`, `review-animations` and `animation-performance` skills.
6. **One coherent, verified increment per commit,** so either builder can backtrack. Schema changes need both builders' agreement (DATA-10).
7. **Tick, then sync.** Tick the item's own checkbox in §3, then run `node scripts/sync-tasks.ts`: it sets the ☑/☐ marks and counts in the priority tables below (`--check` verifies them).
8. **The premium bar (Yash, 29 Oct).** Every surface you touch is clean and premium down to the smallest detail, and information reaches the user with ease (no item-by-item paging, text that says what it is). Product target: $10,000 end to end, for millions of people who only read agent text today. Full statement: [VISION §8](VISION.md), *The premium bar*. Order after SCREEN-1: AUDIT-1, the UI passes, then the motion passes, COMP-1, VIZ-1.
9. **Choosing a model.**
   - Opus for design specs, ambiguous UI direction and reviews.
   - Sonnet is suitable for executing items here that have explicit **Accept** lines.
   - Either model must verify in the browser on actual sessions before ticking.

**How the UI and motion passes are run (Yash, 30 Oct).** One surface at a time, in this order, so that each tool does what it is good at and nothing is polished twice:

1. **AUDIT-1's findings for that surface** are the work list; the passes do not invent their own.
2. **Reviewer lens: the HIG skill** ([dickwu/apple-design-skill](https://github.com/dickwu/apple-design-skill), 123 Apple Human Interface Guideline pages plus a design-craft lens; no licence file in the repository and the pages are Apple's text, so it is installed for the user or cloned under `.local/`, never copied into this repository). Load only the always-load set (accessibility, layout, typography, color, designing for macOS) plus the 3 to 6 pages for what is on screen (sidebars, split views, toolbars, lists and tables, search fields, windows, motion, feedback and loading states), and cite file and heading. Desktop pages only; phone, touch, widgets, Apple Pay and Duo pages are out of scope here. **Its findings are advice, filtered through our doctrine:** Apple's Liquid Glass and translucency do not override the flat, hairline theme with blur only at the header/composer edges (AGENTS creative doctrine 6), and Apple's own warning applies: delight is not decoration.
3. **Worst-case data: `break-ui`** on the surface: long names, one-letter names, thousands of items, zero items, missing fields, non-Latin text. This is the tool for the smallest things in the premium bar.
4. **Craft: `emil-design-eng`** for composition and polish, and the installed **`apple-design`** skill for how things should feel to touch (springs, interruptibility, momentum, reduced motion).
5. **Component libraries (UI-3, Uiverse and others):** only to replace a specific component the audit found weak, never to add one; copy the CSS or markup, add no dependency, check each component's licence, and run it through the freeze, truth and ten-minute tests like anything else.
6. **Then the motion pass, after the UI pass is done:** `find-animation-opportunities` to list what should move and what should not, `improve-animations` for the plan, `animate` and `review-animations` to build and check, `animation-performance` for frame budget. The AGENTS rules hold: motion carries information about origin, relationship or change, or it is cut.
7. **Verify** at 600 and 1440 px on real sessions of both harnesses.

**One pass, concept first (Yash, 30 Oct).** UI-3, UI-4b, UI-7 and UI-8 are one pass (UI-8) over **every component, page and section that comes up**, done as a professional front-end and UX designer would, not component by component in isolation. For each surface the audit answers, in writing, what it is for, what the developer must understand there, what identifies each item, what goes where and how much room it gets, which edges it needs, which controls are primary, how a window opens and what the user returns to, and what its words say (the ten questions are in the [brief](review/ui-pass-brief.md), section 3). Foundations (the token sheet, the spacing, type, radius and border scales, the anatomy of a row, a toolbar, a panel) come first so every surface is built on them. The builder is not a UI expert and expects the advanced thinking from the agent; AUDIT-1, UI-8 and the motion passes may run on Opus.

**Cross-phase ledger (Yash, 30 Oct).** What one phase finds that belongs to another (an audit finding that is a motion idea, a UI decision that changes the backend) is appended to the ledger in the [brief](review/ui-pass-brief.md), section 5, and becomes a TASKS item when it needs work. Every phase reads the ledger first and appends to it last, and thinks through the whole of AUDIT, UI and motion rather than only its own part.

A pilot comes first: run steps 2 to 4 on one surface (UI-16, the Files rail) and compare the result with what the installed skills alone give, before deciding how much weight the HIG skill gets.
