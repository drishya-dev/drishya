# UI-43 — The composer's model menu shows versions and permission modes again

**What went missing.** UI-28 (#370) replaced the old "Connection & permissions" details menu with product menus for model, effort and attach. The model menu listed only each model's display name, dropping the harness's own description (which for Claude Code starts with the version: "Opus 5.5 · …"), and nothing replaced the permission modes: the old menu only *showed* the last reported policy, and the controller never accepted a mode (`turnOptions` refused every key but `model` and `effort`).

**What it does now** (`ComposerMenu.tsx`, `SessionWorkspace.tsx`, `modern/composer.css`; daemon `native-settings.ts`, `controller.ts`):

- **Models:** the name, with the harness's own description as the quiet second line, verbatim (Claude Code: `description`; Codex: `description`, its version is in the display name). Nothing is composed or guessed. Claude Code lists its own "Default (recommended)", so Drishya adds no second Default there.
- **Permissions:** a menu beside the model and effort menus, shown once the harness's list is read. Claude Code: Default, Accept edits, Plan, Bypass permissions (the CLI's `--permission-mode` choices a person can pick). Codex: its own permission profiles from `permissionProfile/list` (Read only, Workspace, Full access), with the harness's `allowed` flag kept: a refused profile is disabled and says so. The current mode is checked (Claude Code: Default, which is exactly how Drishya always launched it; Codex: the sandbox it reports). **Bypass permissions** and **Full access** are in the error colour in the menu and, while chosen, on the trigger with a shield icon and a title that says what it does.
- **Passed through, nothing more:** Claude Code `--permission-mode <mode>` (Default stays `manual` with every request asked in Drishya); Codex `thread/resume` `sandbox`. No `--dangerously-skip-permissions`, no config writes, no `approvalPolicy` sent. The daemon refuses a mode the harness does not offer, one it reports as not allowed, another harness's mode, or anything that is not a plain mode id. The harness still enforces its own policy (managed settings, requirements, safe mode).
- **Never the default:** a mode is sent only when the person picked one for that prompt. Choosing is explicit and is shown again after the prompt is sent.

**Checked.** Units: `apps/daemon/test/controller.test.ts` (each mode reaches the launch or the resume; refusals). Browser: `tests/browser/composer-model-menu.spec.ts` (menu contents, current mode checked, bypass marked, chosen mode is what the next turn is launched or resumed with, 1440 and 600). Real CLIs on a throwaway repository in a scratch Drishya home: Claude Code 2.1.316 and Codex 0.165.0 report 5 and 8 models, every one with a description, and the permission lists above; resuming with each mode, the harness itself reported that mode back (Claude `init.permissionMode`: plan, acceptEdits, bypassPermissions, default; Codex `thread/resume`: readOnly, workspaceWrite, dangerFullAccess), and History showed "Accepts edits", "Bypasses permissions", "Asks before edits" from Claude Code's own journal. The turns themselves could not complete (Claude Code OAuth expired, Codex usage limit), so the journal's recorded mode was checked for Claude Code only.

**For the reviewer.** Non-negotiable 1 says Drishya must not weaken sandbox or approval policy. Choosing Bypass or Full access is the person's explicit choice for one prompt, passed through the supported flag, never a default, and marked dangerous everywhere it shows; say so if that reads as too far.
