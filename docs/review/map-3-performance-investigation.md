## What the new trace establishes

The private synthetic phase probe retains the existing 10,101-observation / 5,000-file / five 200-record additions workload and adds 20 ms process RSS samples, 50 ms main-isolate samples, existing worker-heap diagnostics and phase markers. It changes no production source, input content or resource limit. Raw traces stay ignored in `.local/map-3/` (`bench-phases.ts`, `map-phases-samples.json`, `map-phases.log`). It is a diagnostic run, not replacement acceptance.

In that run:

- Before import: 169.4 MiB RSS; after import: 268.9 MiB; viewer ready: 407.0 MiB.
- A burst reached 183.8 MiB **main-isolate used heap**. At the start of app shutdown, main heap was 97.2 MiB used; worker heap was 34.0 MiB used / 54.4 MiB physical / 18.5 MiB external. Do not add RSS from the worker to process RSS: it is already included.
- After browser close: 433.1 MiB RSS; after server close: 443.0 MiB. The trace's **487.2 MiB maximum was inside `App.close()`**, before its completion; after completion: 408.2 MiB.
- `App.close()` closes ingest, then history, then the captured store. History close may call `saveCheckpoint()`; `ProjectionFold.checkpoint()` serializes the live reducer state and binds its bytes into SQLite. This is a concrete allocation path to isolate. The trace does not establish whether serialization, SQLite/store closure, or another close-time allocation owns all of the peak, and does not prove the earlier 525.2 MiB run peaked in the same phase.
- `exportState()` returns references to reducer state. It does **not** structured-clone the entire reducer before serialization. A theory that this call itself deep-clones all state is contradicted by the code.

## Confirmed follow-up findings and fixes, 21 November

The user explicitly authorized one fixer agent after the investigation. That agent reproduced the restoration defect and fixture contamination, implemented their initial patches, and prepared focus diagnostics/regression material. The parent reviewed the patches, completed the focus regression/fix and discovered two additional allocation defects. No other agents or chats were launched.

- **Host-dependent synthetic fixtures:** Home requests `/v1/sources`, which invokes real adapter discovery, and `/v1/changes` starts default native-folder watches. The benchmark and browser suite previously used those defaults. The import-security unit likewise scanned native folders before rejecting an arbitrary file. Canary tests reproduced the contamination. `9c7c7e53` scopes the synthetic browser suite to disposable harness homes before adapter imports and limits the server test's discovery list to its actual synthetic fixture, preserving parsing/import/privacy and positive/negative security checks. It restores process-local environment/PATH, never native configuration. Actual discovery of explicitly written synthetic records is still tested.
- **Late session restoration:** `235ab8e1` restores saved UI choices before awaiting recording/history data; the response no longer spreads a stale location over deliberate subsequent navigation. A controlled-delay test failed before and passed after. This establishes a real race, not proof that it caused the original post-render narrow Explore failure.
- **Stale tool-trail focus:** the tool-event handler incremented its epoch but never checked it after awaited material arrival; its keyboard counterpart already did. The controlled browser regression held the real two-frame arrival boundary, returned focus to the tool search's Escape summary, then released the arrival. It failed because the history card stole focus. `7f956a74` checks the epoch before and after navigation, retaining the requested `3 of 3` selection without reclaiming focus. The regression and related Toolbox/tool-trail/reading suites passed **19 / one existing opt-in real-session skip, three workers**. This is a demonstrated cause of focus theft; no speculative Disclosure rewrite was made.
- **Discovery-title backing strings:** 200 invented 180,000-character prompts yielded only 32,000 displayed title characters but retained **34.285 MiB** of extra live heap. Copying only the bounded titles released that storage. `2edacc34` detaches the already-sanitized 160-code-unit title with UTF-16 storage; exact redaction/truncation and isolated-surrogate tests preserve existing values. `scripts/bench-discovery-retention.ts` failed before, then measured **+0.16 MiB Codex / approximately zero Claude**. Its exposed GC is diagnostic-only to isolate retained heap, never production behavior or aggregate-RSS certification.
- **Oversized discovery read capacity:** reading a 53-byte journal allocated a 262,144-byte head buffer. A failing allocation-budget regression demonstrated this; `2edacc34` bounds capacity by available file size and the unchanged read limit. Across 200 tiny reads, allocation fell **52,428,800 → 10,600 bytes**. Existing head/tail malformed/clipped-record and adapter discovery checks pass. This removes proven allocation waste, not proof that it alone explains an RSS peak.
- **Cross-test reading recovery:** the final original-case browser batch reproduced the 600 px command failure (16 passed / one failed at three workers). The shared daemon retained saved expansion even though the next test had a fresh browser context. A controlled test seeded that expansion through the actual working-locations API and failed because the command card was expanded, with no collapsed `.op-body`. The fixture-opening helper now clears only its own daemon's saved reading metadata before each content-layout journey. The full content suite then passed **13/13**, configured three workers but effectively one file worker, including both 600/1440 command cases. Production recovery and all whole-line/copy/clipping assertions remain unchanged. This proves a concrete test-isolation failure path, not that every prior card timeout had that cause.

Checkpoint instrumentation isolated a **12,640,074-byte serialized checkpoint**; serialization and its SQLite write added approximately **31 MiB** during close in that run, and database close released approximately 23 MiB. No production checkpoint was disabled, compressed or rewritten: this measured cost is not by itself evidence of a leak. Another trace showed pending work draining during server close. The main-isolate physical heap remains substantially above used heap in some host runs, consistent with allocation/GC high-water effects; exact residual ownership is still unproved.
